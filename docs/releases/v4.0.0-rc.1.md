# Data Plane v4.0.0-rc.1

This is a prerelease for testing the coordinated plugin-capable release set.
Hosted candidate gates and artifact qualification are separate requirements;
these notes do not establish that they have passed.

This release adds a per-Environment deployment queue, safe dispatch of
Deployments requested by first-party plugins (`v1alpha`) and an audited
acknowledgement for unknown plugin-dispatched outcomes. Plugin features stay off
unless the operator enables them.

## What changes

- Deploy and rollback accept `when_busy` (`reject` or `queue`),
  `queue_ttl_seconds` and `expected_base_deployment_id`. A queued request
  returns `202` with a queue item; an idle Environment still returns `201` with
  the Deployment. The raw API default is `queue` (see below).
- Queue endpoints `/orgs/{orgId}/deployment-queue` (list, get, cancel). Items
  are dispatched in order, survive restarts, expire after their TTL and are
  cancelled when the Environment is deleted. Destroy waits for a running
  Deployment instead of ending in `delete_failed`, retrying separately without a
  queue item. Plan-only runs are never queued.
- Optional `halt_on_failure` per queued request: the item is rejected with
  `previous_deployment_failed` when the Deployment it waited for failed.
- A settled queue item names the Deployment its reason refers to in
  `reason_deployment_id`: the failed one for `previous_deployment_failed`, the
  fencing one for `outcome_unreconciled`, the Environment's current one for
  `deployment_base_changed`. Clients need not parse `reason_message`.
- New 409 codes: `environment_busy`, `deployment_queue_full`,
  `deployment_base_changed`, `outcome_unreconciled`.
- Settings: `DEPLOYMENT_QUEUE_MAX_DEPTH` (10), `DEPLOYMENT_QUEUE_DEFAULT_TTL`
  (2h), `DEPLOYMENT_QUEUE_MAX_TTL` (24h).
- External Deployment API for plugins with immutable plans, receipts, protected
  logs and outputs, and Orchestrator admission (off by default,
  `EXTERNAL_DEPLOYMENT_ENABLED`).
- An unknown Runner outcome of a plugin-dispatched Deployment fences its
  Environment until an authorised user acknowledges it through the Control
  Plane. `last-deployments` reports `environment_fence` with
  `remedy_available_at`. The fence never applies to ordinary Deployments.
- Runner timeouts bind to the durable dispatch; late results are retained.
- The admission checker token (`EXTERNAL_DEPLOYMENT_CORE_BEARER_TOKEN_FILE`, and
  for Deployment admission callbacks
  `DEPLOYMENT_ADMISSION_CORE_BEARER_TOKEN_FILE`) must belong to a static-token
  IAM platform principal, which belongs to no organisation and holds no role. A
  service user of an organisation is refused by the Control Plane. The Data
  Plane holds one token for every organisation. Create it with
  `octl plugin-manager create-identities` or `POST /platform-principals`, and
  replace it by regenerating the token. This is a configuration requirement when
  enabling admission callbacks.

## Behaviour changes without plugins

- **A deploy or rollback on a busy Environment now waits in the Environment's
  queue by default (202 with a queue item) instead of failing.** `when_busy`
  defaults to `queue`; send `when_busy: reject` to keep the old fail-fast
  answer, 409 with `error` `environment_busy`. Organisation tokens cannot queue
  (no user to re-check at promotion) and keep getting 409 `environment_busy`.
- Deploy, rollback and destroy take a per-Environment lease; the busy answer's
  message is now "environment has an active deployment lease" instead of "still
  executing". Clients that match the old message text must switch to the `error`
  code.
- Plan-only requests and dry runs are never queued and no longer answer 400 when
  queue fields are sent. While Deployments run or wait they carry
  `pending_changes` (`result_may_change`, running and queued counts). A
  plan-only still answers 409 while another Runner of the Environment runs.
- The one-hour Runner execution budget starts at the first durable dispatch
  attempt, not at admission.

## Data, migration and recovery

Back up the Data Plane database and key storage and drain active Deployments;
the Data Plane applies migrations 21 to 35 when it starts. They add tables and
columns; migration 31 records a dispatch budget for every existing Deployment.
Numbers 17 to 20 are intentionally unused. For recovery, use a compatible
post-upgrade Helm revision with the new binaries and schema. A configuration
rollback keeps data; it is not a database downgrade or proof of compatibility
with older binaries. Data Plane 3.2.0 starts on the newer schema without
checking it; do not go back to it. From 4.0.0 the Data Plane refuses to start on
a schema newer than its own migrations ("database schema version N is newer than
this binary's latest migration 35"). Do not run Down migrations as a rollback;
migration 33 refuses its Down step while queued items exist.

## Plugin contract limits

The plugin contract is `v1alpha`, supported for first-party Stellwerk plugins
only. It is not a stable partner SDK and may change in a later minor release.

## Go contract

`shared/v2.2.0` publishes the additive queue, acknowledgement and external
Deployment client under
`github.com/stellwerk-labs/platform-orchestrator-dp/shared/v2` (Go 1.24). The
application tag does not publish the SDK.

## Compatible candidate set

1.4.0-rc.1, CLI 2.1.0-rc.1, Terraform/OpenTofu provider 2.1.0-rc.1 and plugin
runtime 0.1.0-rc.1 with chart 0.8.0-rc.1. These are coordinated candidate
targets, not a claim that every artifact is available or qualified. The
published Go SDK versions above remain stable contract module tags.
