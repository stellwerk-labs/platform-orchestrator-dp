# Data Plane 4.5.0-rc.3

Pipeline-backed deployments expose Plan, approval, Apply and supported task outcomes through the deployment API. Ordinary deployment behavior remains direct Apply unless a Plan or reviewed published pipeline is selected.

An explicitly retained Plan can be applied once while its captured state, source, recipe and target still match. A stale or superseded Plan requires a new linked Plan and review; retries do not silently substitute new execution material. Delivery replay preserves the accepted command and recorded result rather than starting another Apply.

The deployment view distinguishes infrastructure application from completion of the whole pipeline. If a post-Apply step fails, infrastructure can already be applied while the overall pipeline remains unsettled. Supported repair controls operate on the failed task under its declared retry contract. An unknown infrastructure effect stays held for reconciliation and is not automatically repeated.

Native admission binds the immutable published recipe, Runner UUID, target authority and capability checks before dispatch. Phase-specific encrypted log captures use scoped selectors and retain the dedicated deployment-log permission for decrypted access.

Restored coordinators support `RESTORE_QUARANTINE=true`, which refuses startup before database access, migrations or workers. Operators must fence old writers and reconcile surviving central and site histories before resuming. A missing row in an older backup does not prove that an operation never ran.

Use the coordinated Core, IAM and Runner candidates. Native production use requires the documented durable PostgreSQL, trust, storage and recovery profile; this candidate does not enable Native production activation automatically.
