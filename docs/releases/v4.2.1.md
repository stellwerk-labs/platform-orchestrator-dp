# Data Plane 4.2.1

A PostgreSQL custom-format backup containing successful Draft-test Deployments
can fail during `pg_restore` with `valid_draft_test_reference(jsonb) does not
exist`, even though that function was restored. The two outer CHECK validators
previously resolved their nested function through the restore session's empty
search path.

Migration 40 assigns each existing validator a fixed search path: `pg_catalog`,
the actual schema owning `deployments`, then `pg_temp`. This supports the normal
public schema and installations using another application schema. It changes
neither validator bodies nor constraint acceptance, function OIDs, owners,
privileges, volatility or security-invoker behavior. Other function settings are
preserved. Existing Draft provenance and ordinary deployment rows are unchanged.
There is no API, SDK, dependency or Runner protocol change.

Backups created before migration 40 that contain Draft-test data (schema versions
37–39) retain the broken function metadata. They require the staged pre-data →
schema-qualified metadata repair → data/post-data → normal migration 40 procedure
in [Restoring deployment backups](../operations/restoring-draft-deployments.md).
Do not migrate the target before restoring its archived Goose history. Archives
created after migration 40 restore normally without this repair. A repaired
historical restore is explicitly distinct from byte-identical restoration.

The logical Down for 40 deliberately retains these older-binary-compatible
function settings rather than reopening caller-dependent resolution. This is
not an operational rollback procedure: use a matching forward-compatible DP
binary and verify backup/restore before retiring data. DP binaries whose newest
migration is 39 refuse a database recorded at 40 through the existing schema fence.
